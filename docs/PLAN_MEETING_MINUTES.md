# 设计：会议纪要（2026-10-27；自动整理、聊天接入和人写纪要上传已实现）

## 要解决的问题

问“某次会定了哪些事”时，分身要能说全。现在的做法是从整场会里挑 16 段原话交给模型：按日期问整场会的题，得分从 64% 升到了 80%，但 40 题里仍有 14 题只答对一部分。一场三小时的会只看 16 段，难免漏事。

会议纪要是一场会的结论清单，可以补上这块。**不能假设每场录音都有人写的纪要**：有的会有人整理过，大多数没有。所以两种来源都要支持：

- **人写的纪要**：有就用，它最可信。
- **自动整理的纪要**：没有人写的纪要时，由模型读整场转写生成。每场转写完都能有一份。

## 范围

一期做：

1. 每场录音都有一份纪要：有人写的就用人写的，否则自动整理。
2. 聊天时问到某场会，先给模型看纪要，再给原话片段做出处。
3. 纪要每一条都带原话出处（转写的行号），回答可以引用、核对。
4. 人写纪要可以批量上传，按日期自动配到录音；配不上的由人选。录音是批量上传的，纪要也得能批量挂。

一期不做：

- 纪要编辑器。人写的纪要整份上传或替换，不在页面里逐条改。
- 跨会议的纪要汇总（“这个月定了哪些事”）。
- 纪要推送、分发。

## 纪要挂在录音上，不挂在分身上

纪要描述的是一场会，不属于某一个人。挂在录音库的录音上：

- **一场会只整理一次**：一场 13 人的周会，每个人的分身都用同一份纪要，不用生成 13 次。
- **能升到组织层**：个人分身是底座，团队和组织是方向。纪要是组织层对象，以后“团队记忆”“组织大脑”可以直接用。
- **跟着转写走**：转写重转或校对后，纪要依据的那版转写就过期了，要重新整理。用哪个字段判断转写换了版本（`transcript_id` 或校对标记 `proofread`），实现时再核实。

分身的数据库不存纪要。聊天时按这场会的录音编号去录音库取。

## 数据

在录音库（`media/library.py`）里新加一张表 `minutes`，每场录音每种来源一行（主键 `recording_id` + `origin`）：

| 字段 | 说明 |
|---|---|
| `recording_id` | 哪场录音 |
| `transcript_id` | 整理时依据的转写版本，和当前转写不一致就算过期 |
| `origin` | `auto`（自动整理）或 `human`（人写） |
| `version` | 自动整理的规则版本 `MINUTES_VERSION`，做法和账本的 `LEDGER_VERSION` 一样 |
| `points` | 纪要条目的 JSON 列表 |
| `dropped` | 模型给出、但在原文里找不到出处而丢掉的条数 |
| `error` | 整理失败的原因；有它时 `points` 为空 |
| `created_at` | |
| `document` | 人写纪要的原文件（文件名、sha256、第几场），只有 `human` 才有 |
| `body` | 人写纪要的原文；拆条在后台做（`Libraries.run_written`，规则版本 `WRITTEN_VERSION`） |
| `how` | 人写纪要是怎么配上的：`当天唯一`、`时刻相近`、`内容最像`、`人选` 或 `单场添加` |

待配对的纪要另放一张表 `minutes_pending`：上传人、文件、第几场、标题、日期、原文、建议的录音和配对结果。点“挂上”才搬进 `minutes`。

每一条纪要（point）：

```json
{
  "kind": "决定 | 安排 | 要求 | 待定",
  "text": "王总二月底前把季度预算方案报给管理层",
  "owner": "王总",
  "due": "2026-02-28",
  "lines": [1032, 1035]
}
```

- `lines` 是转写里的行号，即分身资料里的 `src#01032`，回答引用它就和引用原话一样。
- 人写的纪要没有行号，整理时按文字匹配补上最接近的原话；匹配不上就留空，这一条照样可用，但不能当原话引用。

## 两种来源

### 自动整理

- **整理方式**：模型读整场转写，列出这场会定下的事项，每条注明说话行号。会议长于约 40,000 字时分段整理，再合并去重，这一步沿用账本的分窗口做法（`ledger.WINDOW_CHARS`）。
- **什么时候整理**：录音转写完、有人被确认、校对完以后，在后台整理（`Libraries.run_minutes`，排在辨认说话人和校对之后），和分身构建一样受额度限制，额度用完就排队。已有的录音按会议日期从近到远补整理，一次一场。
- **失败**：模型调用出错（服务不可用等）不写结果，一小时后再试；连续失败 3 次记下错误，不再整理，直到 `MINUTES_VERSION` 提升。
- **成本**：daw 现有 334 场录音、约 961 小时。按一场三小时、转写约 8 万字估算，补整理一遍约需 1,700 万输入 token；之后每场新会多一次调用。
- **质量门槛**：每条纪要都要能在原文里找到出处。找不到出处的条目丢掉，丢掉的条数记日志，这和账本的 quote 校验是同一套做法。

### 人写的纪要

- **单场入口**：录音库里录音那一行的“⋯”菜单加一项“添加纪要”，上传 txt、md 或 docx。不加新页面，也不常驻按钮。
- **批量入口**：一批纪要文件直接拖进录音库，和拖录音一样，按下面的规则配到录音。
- **和文字转写分开**：录音库本来就收文字转写。区分方法是看能不能读出说话人轮次（`parse_turns`）：读得出的是转写，照旧走“导入转写稿”；读不出的当纪要。
- **解析**：把纪要拆成条目。人写的纪要格式五花八门，所以拆条交给模型，原文不改；拆好后按文字匹配补行号：和某一行转写的字对（相邻两字）重合 ≥ 40% 的取那一行，否则试相邻两行，都不够就不补。
- **优先级**：
  - 有人写纪要的录音，聊天先用人写的。
  - 自动整理的那份也保留，用来补人写纪要漏掉的事，在资料里标为“自动整理”。
  - 人写纪要删掉后，退回只用自动整理。
- **换掉或移除**：配错了，在那场录音的“⋯”里换一份或移除，之后退回只用自动整理。

### 批量上传，按日期自动配录音

**纪要的日期**：
- 先看文件名，用和录音同一套规则（`util.date_from_name`），`190708_1834`、`2019-07-08`、`2019年7月8日` 都认。
- 文件名没有日期，就看正文开头约 12 行，例如“会议时间：2019年7月8日 18:30”，做法同 `persona.sources` 读文档日期。
- 能读到时刻的，一并记下。

**一份文件写了几场会**：常见的是一份“7月纪要汇总.docx”。正文里有两个以上不同日期的标题（如“7月8日周会”）时，按标题拆成几份，各自配录音，确认卡片上写作“文件名 · 第 N 场”。

**同一份文件再传一次**：按 sha256 认出来，跳过不重复挂，卡片上记一句“重复 N 份已跳过”。内容改过的新版本不算重复，按“这场已有纪要”进待配对。

**按顺序配**：
1. 当天只有一场录音：直接配上。
2. 当天有多场：
   - 纪要里有时刻的，比录音文件名里的时刻（`_1834` 即 18:34）或录音创建时间，相差 90 分钟以内且最接近的那场配上。
   - 没有时刻的，拿纪要正文和当天每场的转写比字对重合比例，第一名 ≥ 20% 且是第二名的 1.2 倍以上才配上。
   - 都分不出来的，不自动配，留给人选。
3. 当天没有录音，或纪要里找不到日期：进“待配对”。
4. 已经有人写纪要的录音，又配到一份新的：不覆盖，也进“待配对”，由人决定换不换。

**daw 上的录音能配上多少**（2026-10-27 只读计数）：
- 334 场录音分布在 294 天，其中 266 天只有一场，按日期就能配上，约占八成。
- 28 天有多场，共 62 场，要靠时刻或内容区分。
- 6 场录音没有日期，只能手动挂。

**上传中**：纪要和录音、转写可以混在一批里拖进来。录音照常上传；文本文件先送去读（`POST /api/library/minutes/read`），读出是转写的退回“导入转写稿”，其余当纪要，读的时候录音库顶部显示“读纪要中…”。只读日期、做配对，不调用模型，几百份几秒到几十秒就能读完。拆条和补行号在挂上之后才在后台做。

**确认卡片**：读完后在录音库就地弹一张卡片，不开新页面。
- 自动配上的折叠成一行，例如“已配上 183 份”，点开可以逐条检查、取消。
- 要人选的、待配对的逐行列出：一行一份纪要，下拉选录音，下拉里按日期从近到远列当天前后的录音。
- 点“挂上”才写入。关掉卡片或点“稍后再选”的话，没选的那些留在“待配对”。录音库顶部显示一行“N 份纪要待配对 · 去选”，选完这行就消失；不常驻，也不弹窗打断。

**记录**：每份人写纪要记下是怎么配上的（日期唯一、时刻、内容，或人选），以后用来统计自动配对认错了多少。

## 聊天怎么用

- **点名某场会时**：比如“7月8号那次会定了什么”“上上次开会”。
  - 资料里先放这场会的纪要，再放原话片段。
  - 纪要标明来源：人写，或自动整理。
  - 问题问的是整场会时，原话片段就用现在铺满整场的做法，给纪要条目做旁证。
- **没点名会议时**：一期不放纪要。二期把纪要条目当作一类检索资料，像账本条目一样参与排序，这样“哪次会定的”“谁负责”这类题也能直接命中纪要。
- **权限**：纪要跟着录音走。分身能看到这场会，才能用它的纪要。别人的名字按分身现有的化名规则处理，和原话片段一致。

## 和承诺账本的关系

账本是从“本人”视角记的承诺和异议，按分身各记一份，可以审核和追踪状态；纪要是整场会的结论，人人共用。两者一期分开，不互相替代。

二期可以考虑让账本直接从纪要派生，少读一遍转写。前提是纪要质量先过评测。

## 评测与验收

- **日期题**：沿用 `~/twin-eval-meetings/time.json` 里按日期问整场会的 40 题，目标从 80% 提到 90% 以上。
- **普通题**：171 题不能退步，没点名会议的题得分应保持不变。
- **评测偏差**：参考答案本身就是模型读全文整理的，和自动纪要是同一种做法，分数会偏高。所以另外抽 20 场会，由负责人核对纪要条目，看有没有漏掉或编造的事项。
- **出处**：每条纪要都能在原文里找到出处的比例要 ≥ 95%。
- **时长**：纪要比原话片段短，回答时长不应变长。

## 上线步骤

1. ✓ 建表，实现自动整理，先在本机一位负责人分身副本的 171 场会上生成纪要并跑评测：日期题 83.5→88.4%，按日期问整场会 80→88.8%，普通题不退。
2. ✓ 聊天接入：问题点名会议时（`meeting_window`），按分身来源编号找到录音（`minutes.recording_of`），每次提问时从录音库读纪要，放在会议片段前面；别人的名字按分身的化名规则替换；最多 120 条，从最近的会取起。
3. ✓ 人写纪要（`web/minutes.py`）：
   - 单场：录音“⋯”里“添加纪要 / 换一份纪要 / 移除纪要”（`POST`、`DELETE /api/library/recordings/{id}/minutes`），有人写纪要的录音行加“纪要”标记。
   - 批量：录音库菜单“上传纪要”或直接拖进来，读完弹“挂上纪要”卡片（`GET /api/library/minutes/pending`、`POST /api/library/minutes/attach`），没选的留在“N 份纪要待配对 · 去选”。
   - 聊天：同一场会人写的在前、自动整理的在后，各自标明。
4. ✓ 自动整理已发布到 stable（1767469a），daw 在后台从近到远补整理。人写纪要上传待发布。
