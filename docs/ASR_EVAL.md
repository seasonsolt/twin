# 语音识别评测

`twin eval-asr` 在本机用同一批带人工标注的片段比较多个识别引擎，给出字错率（CER）、速度和逐条配对比较，用来判断换模型、改参数能不能让会议转写更准。第一个引擎是基线，通常是线上的 asr-funasr 包：1.2.0 起识别用 SeACo-Paraformer 加标点模型，1.1.0 及以前用 SenseVoiceSmall。

## 分层

转写链路分层评测，每层只换一个变量，相邻两层同一批音频上的指标差就是这一层造成的损失，用来判断该先优化哪一层。

| 层 | 测什么 | 命令 | 主指标 |
| --- | --- | --- | --- |
| L1 模型层 | 识别模型本身，输入人工切好的单人片段 | `twin eval-asr` | CER（strict / nofill） |
| L2 切分层 | VAD 与声纹窗口切分，输入整场录音 | `twin eval-asr-session` | 不分说话人的整场 CER、漏检/误检语音 |
| L3 说话人层 | 声纹聚类与本人认领 | `twin eval-asr-session` | DER（collar 0.25 秒）、cpCER、自动认领正确/认错/未认领 |
| L4 后处理层 | 热词、LLM 清洗（已默认开启） | 缓存清洗后用 `twin eval-asr-session` 评分 | CER 差、专名召回、语气词保留 |
| L5 流程层 | twin 记到本人名下的文字 | `twin eval-asr-session` | 本人话语 CER、他人误归属 |
| L6 下游层 | 转写误差对记忆的影响 | `twin eval-asr-memory` | 记忆 precision / recall / F1、重复抽取与裁判噪声 |

L4、L6 使用 AliMeeting 公开标注；L4 的专名召回和语气词保留尚无独立指标。L6 比较同一人次从不同转写建立的单来源记忆，不替代真实个人长期记忆或聊天质量评测。

## 数据

清单是 JSON Lines，每行 `{"id", "audio", "text", "duration", "group"?}`：`audio` 相对清单所在目录，`text` 是人工参考文本，`duration` 为秒，`group` 是可选的录音编号。同一录音的片段错误相关，有 `group` 时置信区间按整段录音重抽，抽样也让同一录音整体落在同一边；没有时每条自成一组。

公开基准用 [WenetSpeech](https://github.com/wenet-e2e/WenetSpeech) `test_meeting`（8370 条、15.2 小时真实会议，中文），Hugging Face 镜像 `lmms-lab-audio/WenetSpeech` 的 `data/test_meeting-*.parquet` 约 220 MB。这份镜像没有录音编号，区间按单条重抽，会偏窄。转成清单（仓库外目录）：

```bash
uv run deploy/asr-eval/prepare_wenetspeech.py test_meeting-00000-of-00001.parquet --out ~/asr-eval/wenet-meeting
```

自建的本人会议片段也写成同样的清单即可，记得填 `group`。清单、音频、输出和缓存都不入 git；`--out` 与缓存目录在 git 仓库内时拒绝运行（`--allow-in-repo` 例外）。

## 引擎

引擎写在 TOML 里，每个 `[[engine]]` 用自己的 Python 运行 `deploy/asr-eval/` 下的脚本，模型依赖不进入 twin 环境：

```toml
[[engine]]
name = "asr-funasr"          # 基线：线上识别路径；pack 默认为已安装的 current，python 默认为包的 venv
kind = "asr-funasr"
pack = "deploy/compute/asr-funasr"   # 也可指向仓库里的包源码（相对运行目录），评测还没安装的改动
python = "~/Library/Application Support/twin/compute/asr-funasr/1.2.0/venv/bin/python"

[[engine]]
name = "sensevoice"          # 模型用包内同一份权重
kind = "sensevoice"
pack = "~/Library/Application Support/twin/compute/asr-funasr/1.1.0"   # 默认为已安装的 current；1.2.0 起不含 SenseVoice

[[engine]]
name = "qwen3-asr-1.7b-8bit"
kind = "qwen3-mlx"
python = "~/.local/share/voxcpm2-mlx/venv/bin/python"   # 装有 mlx-audio 的环境
model = "~/.cache/huggingface/hub/models--mlx-community--Qwen3-ASR-1.7B-8bit/snapshots/<commit>"
options = { batch_size = 32 }
```

- `asr-funasr`：加载包目录里的 `run.py`，构造它的 `Engine` 并调用 `Engine.recognize()`，识别、热词与标点都与线上相同，每批段数取包的设置（MPS 16）。片段已切好，不跑 VAD 和声纹。引擎身份含包的 `pack.toml` 与 `run.py`，改了识别代码就会重新转写。options 可设 `device` 与 `hotwords`（字符串列表）。需要 1.2.0 及以后的包。
- `sensevoice`：参数对齐 `deploy/compute/asr-funasr/run.py` 转写 VAD 片段的方式：MPS、每批 16 段、`language=zh`、`use_itn=True`。片段已切好，不跑 VAD 和声纹。options 可设 `device`、`batch_size`、`language`。包里没有 SenseVoiceSmall（1.2.0 及以后）时引擎直接报错，用 `pack` 指向旧版本目录。
- `qwen3-mlx`：Qwen3-ASR 经 mlx-audio，贪心解码，`language` 默认 `Chinese`、`max_tokens` 默认 512、`batch_size` 默认 32。
- `fun-asr-nano`：Fun-ASR-Nano-2512 经 Transformers 原生实现（`transformers>=5.17`，不加载远程代码），model 为 `FunAudioLLM/Fun-ASR-Nano-2512-hf` 的本机目录。MPS、float32、贪心解码；options 可设 `device`、`dtype`、`batch_size`（默认 16）、`language`（默认 `zh`）、`max_new_tokens`（默认 256）。
- `fireredasr2-aed`：FireRedASR2-AED，python 为装有 `fireredasr2s` 和 `kaldi_native_fbank` 的环境，model 为 `FireRedTeam/FireRedASR2-AED` 的本机目录。官方推理只认 CUDA，脚本复用它的特征、模型和分词器，自己放到 MPS 上；解码参数取官方默认（beam 3）。options 可设 `device`、`batch_size`（默认 16）、`beam_size`。

新引擎各用一个独立环境，例如：

```bash
uv venv --python 3.12 ~/.local/share/asr-eval/fun-asr-nano/venv
uv pip install --python ~/.local/share/asr-eval/fun-asr-nano/venv/bin/python \
  transformers==5.17.0 torch==2.10.0 torchaudio==2.10.0 librosa==0.11.0 soundfile==0.13.1
uv venv --python 3.12 ~/.local/share/asr-eval/fireredasr2/venv
uv pip install --python ~/.local/share/asr-eval/fireredasr2/venv/bin/python \
  "fireredasr2s @ git+https://github.com/FireRedTeam/FireRedASR2S@4e7d9aaf4482a47cec1724807026b9b151926eb5" \
  kaldi_native_fbank==1.22.3
huggingface-cli download FunAudioLLM/Fun-ASR-Nano-2512-hf --revision d93b302ee7fd505e1b3576120fc142fc6f7820e1
huggingface-cli download FireRedTeam/FireRedASR2-AED
```

引擎协议：stdin 一个 JSON 请求（`model`、`options`、`items` 列表；sensevoice 另有 `pack`），stdout 每条一行 `{"id", "text", "seconds"}`，日志写 stderr（评测输出目录的 `logs/`）。`--identify` 只打印依赖版本。新增引擎类型时在 `src/twin/evals/asr.py` 的 `KINDS` 登记脚本。

## 运行

```bash
uv run twin eval-asr --manifest ~/asr-eval/wenet-meeting/manifest.jsonl \
  --engines ~/asr-eval/engines.toml --out ~/asr-eval/runs/<日期>-<改动>
```

- **划分。** `--split dev`（默认）日常迭代，`--split formal` 只在阶段结束时跑一次，`--split full` 跑全量。dev 与 formal 是按种子 `asr-v1` 固定、互不重叠的样本，各约 `--size`（默认 1000）条；同一 `group` 不会拆到两边。比较两份成绩单时清单、划分、规模和种子必须相同。
- **缓存。** 每条转写一写出就追加到缓存（默认清单旁的 `asr-cache/`，0600），文件名带引擎身份指纹：引擎脚本、依赖版本、模型文件（sensevoice 为算力包 `pack.toml`，含权重摘要；qwen3-mlx 为模型目录与 `config.json`）和 options。中断后重跑只补缺的条目；引擎不变时重跑只重新算分，约 1 秒；改了任何一项就是新身份，从头转写。
- **输出。** `scorecard.json` / `scorecard.md` 只含汇总；`items.jsonl` 含参考文本和各引擎转写，供逐条查错，权限 0600。

## 评分

- **归一化**与 y15 合成语音评分相同：NFKC、小写、`5.5`→`五点五`、数字逐位转汉字，再按汉字和英文单词切分，标点与空格不计。CER =（替换 + 删除 + 插入）/ 参考字数，按全体字数汇总（不是逐条平均）。
- **两种口径**：`strict` 按参考原文；`nofill` 两边都去掉 `呃嗯啊哦噢唉诶欸哎呀吧呢嘛哈` 等语气词再算。参考文本逐字记了语气词，各模型保留与否只是风格，`nofill` 看实词识别。
- **区间与配对比较**：CER 的 95% 区间按组 bootstrap 2000 次；候选与基线比较时用同一批重抽样本算 CER 差的区间，并数出逐条错字数变好、变差的条数，做双侧精确符号检验。
- **波动下限**：同一引擎的批量推理会把同批片段补成等长，换一批组合，约 10% 的 SenseVoice 转写字面不同，CER 相差约 0.04 点。同一划分每次组批相同，结果可复现；但小于约 0.1 点的差别不要解读为改进。
- **RTF** 为推理秒数 / 音频秒数，不含模型加载；缓存命中的条目沿用当时记录的耗时，换机器后要清缓存重测速度。

## 性能

在 Apple M1 Max 上，`test_meeting` 中 Qwen3-ASR-1.7B 逐条解码的 RTF 约 0.083（15.2 小时全量约 76 分钟）。时间几乎都花在逐词解码上，它受内存带宽限制，所以评测用了下面几招：

| 手段 | 效果 |
| --- | --- |
| dev / formal 约 1000 条（1.8 小时）代替全量 | 两个引擎合计约 4.5 分钟；CER 差的 95% 区间宽约 ±0.3 点，足以分辨 0.5 点以上的变化 |
| Qwen3-ASR 按时长排序、32 条一批解码 | RTF 0.083 → 0.036，全量约 33 分钟；约 8% 转写字面变化，CER 变化在 0.1 点内，因此批大小计入引擎身份 |
| 转写缓存按引擎身份复用 | 只改评分或只加一个新引擎时，其他引擎不再运行 |
| 引擎常驻一个进程 | 模型只加载一次（SenseVoice 冷启动约 17 秒） |

批大小再加到 32 以上收益递减：同批每段仍逐段编码音频，编码约占批量解码时间的三分之一。

## 整场评测

`twin eval-asr-session` 用 twin 上传录音时同一套 `CommandTranscriber` 与 `analyse()` 跑整场会议，被测的就是线上运行的程序。

**数据。** [AliMeeting](https://www.openslr.org/119/)（OpenSLR SLR119，CC BY-SA 4.0）：中文真实会议，每场 2–4 人、15–30 分钟，句级说话人与时间标注（TextGrid）。Eval 8 场 4 小时（3.42 GB）日常迭代，Test 20 场 10 小时（8.90 GB）阶段结束时跑一次；训练集用不到。解压后转换（仓库外目录）：

```bash
uv run deploy/asr-eval/prepare_alimeeting.py <解压目录>/Eval_Ali --out ~/asr-eval/alimeeting/eval
```

远场取 8 通道阵列的第 0 通道，最接近手机或笔记本单个麦克风；去掉 `(SIL)`、`<sil>` 等标注记号。输出：

- `sessions.jsonl`：每场 `{id, audio, duration, reference, references}`，`reference` 指向 `{"segments": [{start, end, speaker, text}]}`，`references` 为 `{说话人: 参考声音}`。
- `manifest-far.jsonl` / `manifest-near.jsonl`：不与他人重叠的单句，`group` 为场次，直接交给 `twin eval-asr` 得到同一批音频的 L1。近场是干净音频的对照。
- `voices/<说话人>.wav`：约 10 秒不与他人重叠的近场录音，模拟本人参考声音。优先取该说话人最后一场会议，那一场不再把他当「本人」评测；只参加一场的人取同一场的近场录音。AliMeeting Eval/Test 里每人只参加一场，所以全部是同场取样：麦克风不同，但内容与被评的远场重叠，自动认领结果偏乐观，与线上「另录一段本人声音」相比是上限。`sessions.jsonl` 的 `voice_from` 记录取自哪一场；孤立语音不足 5 秒的人没有参考声音。

**引擎。** TOML 的每个 `[[engine]]` 写 `name`、`command`（twin `[asr] command` 的写法），可选 `language`（默认 `zh`）和 `files`（计入引擎身份的文件，如算力包的 `pack.toml`）。线上引擎的 `command` 照抄 `twin.toml` 里 `twin compute install asr-funasr` 写入的那一行；算力包目录随系统而定（macOS 默认 `~/Library/Application Support/twin/compute`，可用 `TWIN_COMPUTE_HOME` 改）：

```toml
[[engine]]
name = "funasr-1.2.0"
command = "'<算力包目录>/asr-funasr/current/venv/bin/python' '<算力包目录>/asr-funasr/current/run.py'"
files = ["<算力包目录>/asr-funasr/current/pack.toml"]
```

**运行。**

```bash
uv run twin eval-asr-session --sessions ~/asr-eval/alimeeting/eval/sessions.jsonl \
  --engines ~/asr-eval/session-engines.toml --out ~/asr-eval/runs/<日期>-<改动>
```

每场按带 `diarize` 的请求转写，一次带上这场所有被评测本人的参考声音（`reference` 加 `references`）。参考声音只影响相似度，不影响识别和聚类；asr-funasr 1.2.1 起一次返回每个说话人对每份声音的相似度，每场只跑一次；更早的包忽略 `references`，评测自动退回每人各跑一次。没有参考声音的场次跑一次。同一次请求还带上其他场次的人（不在这场会议里）的声音，凑满 32 份，看 twin 会不会把不在场的人认领成本人：L3 的「不在场误认」列给出次数和他们与任一说话人的最高相似度，调认领门槛时它必须保持为 0；更早的包不比较多份声音，这一列为「—」。L2 用同一次带 diarize 的输出、忽略说话人：线上开启 diarize 时 `run.py` 按声纹窗口重新切分，与不开启时不同。结果按引擎身份（命令、language、`files` 的摘要）缓存在清单旁的 `asr-cache/`，中断后只补缺的场次。

**评分。** 文字归一化与片段评测相同。

- 整场 CER：参考和输出各按开始时间拼接后对齐（M2MeT 的先入先出口径）。
- DER：逐帧（10 毫秒）漏检 + 误检 + 说话人混淆，除以参考说话人总时长；说话人按共同时长最大的一对一匹配；参考边界两侧各 0.25 秒不计分，另报 collar 0。重叠语音按每帧说话人数计。
- cpCER：每个说话人的话按时间拼接，取总错字最少的说话人对应；没对上的参考说话人全算删除，多出的输出说话人全算插入。
- 自动认领：按线上规则（`media/claim.py`，见 [MEDIA.md](MEDIA.md)）认领后，看每个被认领说话人的时间里谁说得最多：都是本人为正确，否则为认错。
- 本人话语 CER：参考里本人的话对比 twin 记到本人名下的文字；没有自动认领时按用户手动选对说话人计算。另报其中的删除，以及“无重叠句”（本人与他人都不重叠的句子，只计替换和删除）的错误率，用来区分重叠造成的损失和识别本身的损失。他人误归属：本人名下的字里，落在只有别人说话时段的比例。
- 区间按场次 bootstrap；与基线逐场配对，符号检验按场次。Eval 只有 8 场，区间很宽，结论以 Test 为准。

`scorecard.md` 按层分节，末尾给出层间损失（说话人损失 = cpCER − 整场 CER，流程损失 = 本人话语 CER − cpCER）；`items.jsonl` 含每场参考与输出，权限 0600。

## 已有结论

2026-10-12，WenetSpeech `test_meeting` 全量 8370 条，逐条解码：

| 引擎 | 严格 CER | 去口头语 CER | RTF |
| --- | --- | --- | --- |
| SenseVoiceSmall（当时线上） | 7.62% | 7.00% | 0.005 |
| Qwen3-ASR-1.7B 8bit（MLX） | 5.84% | 5.18% | 0.083 |

同日用 `twin eval-asr` 跑的划分基线（Qwen3-ASR 32 条一批，提交前的工作区）：

| 划分 | SenseVoice 严格 CER | Qwen3-ASR 严格 CER | CER 差（95% 区间） | 变好 / 变差 | 用时 |
| --- | --- | --- | --- | --- | --- |
| dev（1000 条，1.79 小时） | 7.38% | 5.84% | −1.54（−1.85 至 −1.23） | 315 / 118 | 4.5 分钟 |
| formal（1000 条） | 8.03% | 5.95% | −2.08（−2.40 至 −1.76） | 363 / 119 | 4.3 分钟 |

全量逐条结果：Qwen3-ASR 的 CER 低 1.78 点（95% 区间 1.69–1.91），相对少错约 23%；逐条看 2860 条更好、1000 条更差。替换和删除都下降，删除从 2.57% 降到 2.01%。官方报告的 bf16 版本在同一测试集为 5.88%，与本机 8bit 一致。Qwen-Audio-3.1 系列只有阿里云 API，没有开放权重，录音须上传，不符合本机离线转写的约定，没有纳入。

2026-10-13，以线上 asr-funasr 1.2.0（SeACo-Paraformer + 标点）为基线，六个引擎各用默认参数（Qwen3-ASR 32 条一批），dev 与 formal 结论一致：

| 引擎 | dev CER | formal CER | formal 比基线（95% 区间） | formal 变好 / 变差 | RTF（dev） |
| --- | --- | --- | --- | --- | --- |
| Paraformer（1.2.0 线上） | 6.81% | 7.00% | — | — | 0.014 |
| SenseVoiceSmall（1.1.0） | 7.38% | 8.03% | +1.03（+0.75 至 +1.30） | 139 / 270 | 0.006 |
| FireRedASR2-AED，beam 3 | **4.58%** | **4.62%** | −2.38（−2.72 至 −2.05） | 383 / 89 | 0.137 |
| FireRedASR2-AED，beam 1 | 4.68% | 4.73% | −2.27（−2.60 至 −1.95） | 384 / 94 | 0.064 |
| Qwen3-ASR-1.7B 8bit | 5.84% | 5.95% | −1.05（−1.35 至 −0.77） | 263 / 139 | 0.036 |
| Fun-ASR-Nano-2512 | 6.44% | 6.44% | −0.56（−0.88 至 −0.26） | 233 / 173 | 0.065 |

- 1.2.0 换成 Paraformer 是实在的改进：比 SenseVoice 少错约 13%（formal 1.03 点）。

## 远场参考声音的认领门槛（2026-10-21）

上面的认领门槛是在 AliMeeting 上定的，那里的参考声音是头戴麦。twin 实际常用从会议片段生成的候选当参考声音（`docs/MEDIA.md`），也就是远场录音。AISHELL-4 留出集（20 场 116 人次，参考声音取自同一阵列第 4 通道）上的情况完全不同：本人最相似的组多在 0.75–0.95，同屋其他人的组到 0.45–0.66（AliMeeting 上其他人都低于 0.45）。按原规则，其他人的组相似度过 0.55 就被追加认领：asr-funasr 1.4.0 的 overlap 流程选对说话人时本人话语 CER 16.08%、误归属 3.72%，按线上规则却是 35.21%、19.76%。

只改认领规则，不重新转写：用 `twin eval-asr-session` 缓存里的分段、说话人和相似度离线重放 `analyse`，打分同 L5（`attributed_counts`、`majority_speaker`）。AISHELL-4 已是 1.4.0 的留出集，按房间切开：R003（12 场 70 人次）比较规则、选门槛，R004（8 场 46 人次）只验证一次。头戴麦对照是 AliMeeting 上所有带缓存的流程：Eval 的 p14-classic、p14-overlap 和 2026-10-20 爬坡的 9 个流程，Test 的 climb-base 和 climb-pyannote，以及 2026-10-13 Eval + Test 的聚类阈值 0.55–0.75、FireRed 共 7 个流程。其中聚类阈值 0.55 和 0.60 会把本人拆成几组，正是追加认领要接住的情况。

R003 上比较过的候选规则：

- 追加认领只要求与最相似者的差距不超过 0.1–0.3。
- 只追加短组：组时长不超过最相似组的 10–50%，或不超过 30–120 秒。
- 只追加声纹接近最相似组的组（两组声纹余弦至少 0.6–0.7）。
- 按场内其他组的中位数归一化。
- 提高追加门槛到 0.6–0.7。
- 完全不追加。
- 最相似者还要领先第二名 0.1–0.2 才认领。

“领先第二名”能把认错首选和不在场误认都压下去，但会让 AliMeeting 少认 1–2 人（被拆出的本人碎组与主体相似度接近），所以不采用。按组时长限制也不行：AliMeeting 上有本人主体排第二、只差 0.011 的情况，它会被挡掉。差距条件最直接：AliMeeting 上本人碎组与最相似者的差距最多 0.194，R003 上被误追加的他人组差距大多在 0.2 以上。

## 小类合并门限（2026-10-20，asr-funasr 1.3.1）

**问题。** 聚类后，总时长低于 floor = max(3 秒, 语音总时长 / 100) 的小类，原来不论相似度都按窗口并入最近的大类。如果一个人只说了几句，他的话就会进别人的说话人；长会议里还会出现一个质心很“泛”的大类，吸走几十个小类。线上 S8（129 段、215 秒，三段试听是三个人）就是这样形成的。

**方法。** 每场的 VAD 片段、1.5 秒窗口和 CAM++ 声纹只算一次并缓存（M1 Max，MPS），聚类之后的步骤离线扫参，DER 用 `twin.evals.diarization.diarization_error`（collar 0.25）。窗口按 `run.py` 切分重建，但不转写，所以空文本的片段也计分。现状这一行的 Eval DER 是 25.7%，与 4090 上的整场评测（25.9%）一致。指标：

- 少言者测试：每场依次选一个人，只保留他随机几段共约 10 / 20 / 40 秒的发言，其余涉及他的窗口全部去掉。统计这段发言最后被并进别人的说话人（≥15 秒、以别人为主）、自成一人，还是成为零碎（<15 秒，团队页的“零碎的声音”）的比例。代价看“他人窗口落入零碎”：本该归到某个大类、却被留在零碎里的秒数。
- 他人混入：≥15 秒的说话人中，非主要参考说话人的单人发言时长占比。
- 真实周会：本机 8790 副本里的一场 2.3 小时会议，没有人工标注，只看说话人数、零碎时长和吸附情况。

真实周会（语音 4825 秒，floor 48 秒，聚类得到 236 类，其中 13 个大类）：强制合并时，有一个大类本身只有约 104 秒，却吸走了 65 个小类共 169 秒（它在 13 个说话人里类内离散度最差）。这些小类离它最近，但比第二近的大类只高 0.06（中位数），第二近的大类分散在其他 12 个说话人上。只加相似度门限挡不住这种吸附（0.5 − 0.2/n 时它还是吸走了 183 秒），加上领先条件后降到 123 秒（≥ 0.05）或 60 秒（≥ 0.1）。代价是零碎 148 / 252 秒（语音的 3% / 5%），≥15 秒的说话人从 13 个变成 17 / 19 个。

## L4：用 LLM 校对缓存转写

[llm_clean.py](../deploy/asr-eval/llm_clean.py) 是仅用于公开评测的两阶段工具，不接入上传流程、不运行 ASR：

1. `prepare` 按清单 ID 从指定的基线缓存取假设文本，同场只清洗一次，再复制到每个本人和不在场声音的视图。不会读取人工参考文本或音频。仅发送说话人编号、原转写和允许编辑的片段编号，须显式加 `--public-alimeeting`；不要用于私人录音。
2. `replay` 按 `CommandTranscriber` 协议回放清洗结果，恢复各参考声音的相似度。时间、说话人、片段数量、说话人列表及各视图的相似度不变；评分仍用未经修改的 `twin eval-asr-session`。

[提示词](../deploy/asr-eval/llm_clean_prompt.txt) 要求只改确定的识别错误，禁止总结、润色、补全残句、跨片段搬词；保留口头语、重复和自我修正。每次提供全场上下文，只返回指定片段的稀疏修改。程序拒绝重复或越界 ID、类型错误和额外字段；空替换及超过编辑距离门槛的修改逐段回退原文。门槛按去标点后的字母数字字符计算，不能保证语义忠实，仍可能把原本正确的词改错。

```bash
# EVAL_ROOT 是仓库外的公开数据目录；TWIN_CONFIG 指向自己的配置。
# 密钥只从环境变量读取，不写入命令或输出文件。
uv run python deploy/asr-eval/llm_clean.py prepare \
  --sessions "$EVAL_ROOT/alimeeting/eval/sessions.jsonl" \
  --base-cache "$EVAL_ROOT/cache/<基线缓存>.jsonl" \
  --config "$TWIN_CONFIG" --public-alimeeting \
  --cache "$EVAL_ROOT/llm-cache" --out "$EVAL_ROOT/runs/<变体>/clean.jsonl" \
  --batch 400 --effort low --guard 0.25 --workers 2
```

响应按服务地址、模型、推理等级、提示词和完整输入的摘要缓存，权限 0600；改变门槛可复用响应，不需再次调用。`clean.metrics.json` 记录调用次数、供应商返回的 token 数、缓存命中、调用耗时、整批墙钟时间和被拒绝的修改。连接错误、HTTP 408/429/5xx 最多重试 4 次，退避 30/60/120/240 秒，并尊重秒数格式的 `Retry-After`；其他 HTTP 错误、耗尽重试或格式错误报错，不把失败伪装成成功清洗。

引擎 TOML 中，基线也可用 `replay --cache <原缓存>`，避免任何 GPU 连接；候选改为 `replay --cache <clean.jsonl>`。`command` 用 twin 环境的 Python 执行脚本；`files` 必须包括脚本、提示词、对应缓存，以及候选的 `clean.metrics.json`，使代码、提示词、参数和结果变化均改变身份。第一个引擎放未清洗基线，照常运行 `twin eval-asr-session --sessions ... --engines ... --out ... --cache ...`。回放得到的 RTF **不是**清洗速度，成本只看 `clean.metrics.json`。

### 建议

**保留评测工具，暂不接入 ingest，更不默认开启。** Paraformer 的 Test 改善是真实且一致的，但只有约 0.25 点，远小于此前聚类的 8.5 点、换识别器的约 1.5–2 点，以及重叠语音留下的二十多点删除。不能据此支持「LLM 清洗是下一步最高收益改进」；它更像有成本的小幅校对。

本任务的上线门槛还要求误归属不升。Paraformer Test 从 3.622111% 升至 3.622480%，**增加 0.000369 个百分点**，严格说没有通过。各声音视图、每段时间与说话人字段已逐项核对完全不变，DER 与认领结果也不变；这极小的变化来自文本长度改变后的比例加权，不能解读为明显的说话人混淆恶化，但也不能把它四舍五入隐藏为「零增长」。不根据 Test 再加长度保护或挑选编辑，否则将是在留出集上调参。

对 twin 的记忆抽取，优先保留逐字证据、口头语及自我修正，交由原有抽取流程决定哪些内容值得记住，不为了文笔先不可逆地删词。当次 L4 尚未做 L6 记忆质量评测（补测见下节），不能从 CER 或阅读流畅度推断记忆一定更好；语义误改、上下文诱导的补写、延迟、服务限流，以及全场文字外发仍是风险。没有接入生产转写流程、修改配置默认值或记忆抽取提示词；后续若探索更严格的保护，应另设独立留出集验证。

## L6：转写质量怎样影响记忆

`eval-asr-memory` 是评测专用路径，复用生产代码，不修改抽取/合并提示词、输出结构或维度版本：

- **人次与输入。** 与 L5 相同，只评清单 `references` 中的人。gold 使用人工参考说话人的原话；asr 和 clean 用同一 `analyse()` 自动认领，无自动认领时按 L5 的共同时长多数说话人规则模拟正确手选，不使用文字匹配来选人。clean 固定为 L4 的 low / 400 段 / 0.25 门槛版本。
- **真实上传路径。** `Analysis.lines()` → `parse_media()` → 临时、隔离的 `PersonaStore` → `consented_facets()` → `chunks_for()` → `extract_chunk()` → `merge_facet()`。保留非本人语句作上传流程原有的上下文，但只有本人条目进入抽取；不会把对方的语境直接算成本人证据。每个输入独立建库、使用匿名名字“本人”、音频来源类型和默认未授权的敏感维度限制，不访问用户数据库。原文引语验证及单细项合并均由生产代码完成。只改变输入，不为金标准调整断句或删除口头语。
- **比较对象。** 评合并后的 `facet_id / statement / applies_when`，并保留非空 `conflict` 警告，不是直接比较原始抽取候选，也不是 CER。裁判只看到 `gold`、`candidate` 的记忆集合和局部编号，不知道候选来自 ASR、清洗还是另一份 gold；不提供音频或转写来替模型补答案。允许不同粒度的一对多匹配。逐 gold 记忆是否被覆盖算 recall；逐 candidate 是否受 gold 支持算 precision；冲突、语义破碎单独计数。`unsupported` 只表示金记忆未覆盖，**不能直接等同幻觉**。
- **噪声与缓存。** 同一 gold 进行两次独立抽取及合并（gold0、gold1），比较 gold1 对 gold0，作为重复性参照，不是理论上限。asr、clean 也各自独立抽取。每种比较再用两个独立裁判请求重复；先在人次内平均，再跨人次汇总。裁判用定长数组紧凑返回同样的逐条编号、匹配编号、状态和实体/数量标记，程序展开后检查两边编号完整性；不通过时只修复一次，仍不通过则报错，不把漏掉的条目当成功。缓存身份包括模型设置摘要、完整提示词、输入、schema、调用选项和独立重复编号；重复编号只进入本地缓存键，不进入模型提示词，避免把一次缓存响应误当两次独立抽取。重跑同一编号免费复用，网络错误退避重试。
- **统计。** 主表为人次等权宏平均 P/R/F1；空集合没有对应分母时记 NA，双空不算满分，非空对空 F1 为 0。clean − asr 在同一人次配对；95% 区间按整场会议 cluster bootstrap 2000 次，以免同场多人被误当独立录音。同时给出人次符号检验和场均差的符号检验。实体/数量子集由裁判标注，属于未经人工核验的诊断指标。

```bash
uv run twin eval-asr-memory \
  --sessions "$EVAL_ROOT/alimeeting/eval/sessions.jsonl" \
  --base-cache "$EVAL_ROOT/cache/<Paraformer缓存>.jsonl" \
  --clean-cache "$EVAL_ROOT/runs/<固定L4方案>/clean.jsonl" \
  --llm-config "$TWIN_CONFIG" --public-alimeeting \
  --cache "$EVAL_ROOT/l6-cache" --out "$EVAL_ROOT/runs/<日期>-l6-eval" --workers 2
```

`--llm-config` 仅读 `[llm]`；提取使用该设置的原生产推理参数，裁判固定 low。`--limit` 仅供 Eval 冒烟检查；Test 使用下述预先固定的一场一人规则，不按评分挑样本。输出 `scorecard.md/json`、逐人次 `items.jsonl` 和中断检查点 `cases/`，含本人文本、记忆和逐条判定，权限 0600；全部必须放仓库外。缓存保存原始结构化模型响应及 usage，不保存密钥。

适用边界：

- AliMeeting 是公开多人会议，能抽到不少观点、方案和表达习惯，但不等于丰富、真实的长期个人经历。gold0 是**金转写上的模型抽取参照**，不是人工逐事实记忆金标准；`unsupported` 不能直接称为幻觉，连 `contradicted` 也仍是模型判定。
- 评的是无历史记忆的单来源抽取/合并，不涵盖跨来源长期合并、聊天检索或最终答复质量。gold 与 ASR 的差还包含认领、切分和上下文差异，不是 CER 到记忆 F1 的换算系数。
- Test 是 18 个预先选定目标的条件结果；不覆盖没有参考声音的两场，也不能当作所有 48 个 L5 目标的分数。L4 CER 是完整 20 场的字符加权值，L6 是该 18 人次的宏平均，两个量纲不能直接比较大小。
- 裁判与抽取使用同一模型、没有人工交叉核验；重复 gold 和重复裁判揭示了噪声，但不是对所有偏差的校正。

### 合并 L4 与 L6 的建议

**不默认开启、不接入当前 ingest；保留为值得进一步验证的 opt-in 实验，而不是仅凭小 CER 改善就断言毫无价值。** L4 Paraformer 的 CER 32.308→32.056%（−0.252 点）很小，但 L6 Test 的记忆 F1 46.27→49.31%、Recall 39.22→42.02% 提示了实际下游增量。它仍远低于约 79% 的 gold 重复参照，无法补回大部分未识别内容。

同时，Eval 主区间跨零，Test 的 F1 符号检验不显著，实体/数字收益未复现，模型噪声不小；误归属的变化（Paraformer +0.000369 点、FireRed +0.000519 点）是计算噪声：清洗不改说话人，不会真正影响归属。下一步若要产品化，应先在另一个、获得授权的个人记忆留出集上做人工事实核验和明确的安全门槛，再决定是否提供 opt-in。当前证据既不足以支持默认上线，也没有与其他改进做 L6 成本对照，**不能证明它是“最高 ROI”步骤**。生产提示词、维度、内核版本与默认转写流程均保持不变。

### 真实录音复核与上线（2026-10-14）

上面的建议后来被推翻。用户用自己的一段 49 分钟培训课录音复核：用户主讲，有课堂互动，内容有 DDD、domain、API 等术语。用 asr-funasr 1.2.1（阈值 0.65）转写，得到 282 段，再用同一提示词、low 推理、每批 80 段、0.25 门槛清洗。LLM 修改了 89 段（32%），另有 3 处超过门槛被拒，共约 8.2 万 token。用户听原声逐段评判，**89 处全部改对**。录音和转写只留在本机，不入库。

AliMeeting 低估清洗收益，主要有四个原因：

- **错误构成不同。** AliMeeting 上 33.8% 的 CER 中，26.3 点是重叠语音里的删除，替换只有 6.5 点。LLM 没有音频，补不回删除，可修的上限本来就小。单人讲课的剩余错误以替换为主。
- **内容不同。** AliMeeting 是日常话题，很少有术语和英文；识别器最容易错的恰好是专业术语，而 LLM 最熟悉它们。同一套设置在 AliMeeting Test 只改了 6.6% 的段（7004 段中 465 段），讲课录音改了 32%。
- **指标稀释。** CER 中每个字等权，修好一个术语只占几个字，但它对记忆和检索最重要。L6 本来用于弥补这一点，但 AliMeeting 的发言人不谈自己的生活，记忆稀薄、噪声大。
- **评测集不像真实使用。** 本文开头已提醒选型前要用本人会议清单复核，L4/L6 的建议却只依据公开集。今后转写相关的决定，应在本人场景的小集（几段本人录音，人工校对其中几分钟，只留本机）上复核后再下结论。

**上线。** 清洗已接入 ingest，**默认开启**（`[asr] clean = true`），实现见 `src/twin/media/clean.py`：

- 转写完成后、认领说话人之前，用 `[llm]` 每批校对 80 段，只能改自己的段。上线时每批都附全场文字，2026-10-20 起改为只附前后各 20 段（见下节）。
- 时间、说话人和段数不变；改动超过 0.25 门槛或改成空文本的编辑会被拒绝。
- 某批失败时保留原文；没有配置文字模型时跳过校对，导入照常完成。
- 成本约每小时录音 10 万 token（这是 49 分钟讲课的数字；附全场文字时成本随时长平方增长，长会议远不止于此，见下节）。转写全文会发往 `[llm]`，与记忆整理发往的服务相同。

- 片段越长越准：3 秒拼接、δ＝0.1 时本人片段误报 1.5–3 秒 13%、3–6 秒 6%、≥6 秒 0.5%（near Eval）。5 秒拼接误报再降 1–2 个百分点，但一句插话会被平均掉，取 3 秒。
- 外人门限只用于 ≥3 秒：1.5–3 秒的本人片段有 25–37% 落在 0.25 以下。
- 片段里混着两个人时（没人占到 80%，约 5–6%），被确认的人占 0–20% 几乎全标出，20–50% 标出 59–85%，50–80% 标出 5–26%，80% 以上 0–2%。
- 说话人级：干净说话人（说了 ≥30 秒）被标出的秒数占比中位数 0–2%，p90 7–21%；四种组合共 151 人中 6 人 ≥20%，多为抢话重叠多的人，最高 47%。所以疑似 ≥20% 才进团队页待处理。

**真实周会（本机 8790 副本，13 位已确认说话人）**：1.3.2 一次请求算完，M1 上 76 秒。自动认出的 4 位本人中位相似度 0.63–0.81，疑似 0%；早期手动确认的说话人里 3 位超过 20%（21%、29%、92%），92% 那位多数片段指向同一位同事，是整位说话人确认错了，“都改给某某”一次改完；另 3 位在 4–16%，不进待处理。

**修复路径**：A＝用 1.3.1（合并门禁）重新转写并迁移确认；B＝记录逐段排除/改归，分身来源跳过这些段并让相关人的 `wanted` 加一。选 B：A 依赖尚未合并的服务包，重新转写会让校对、命名和确认失效并再花一次校对 token，而 1.3.1 的门禁在已知案例里仍会并进约 2 分钟别人的话；B 只动被点到的段，来源 id 按本人段号重算，只有这段录音的来源重新抽取。两者不冲突，1.3.1 上线后新录音混入更少，复核照样兜底。

## 团队录音库流程评测（2026-10-20）

`eval-asr-session` 走的是个人上传路径（带本人参考声音、`analyse()` 认领）。团队录音库走另一条：转写时不传任何声音，之后由 `Team.classify` 按声纹样本认人、`media.review` 逐段复核。`twin eval-asr-library` 在临时录音库里用生产代码跑这一条，按人工参考评分：

1. `Library.transcribe`（diarize，`reference=None`、`references={}`，与线上一致）。
2. 每份参考声音建成一个人，声纹存为一段「别的录音」的样本；`Team.classify` 只看声音自动归属。
3. 主人由预言机模拟：没归属的说话人确认成其中说话最多的人（没有这个人就新建）。
4. `Reviews.run` 逐段复核，按参考标注判断标出的段是否真是别人的；再分三种情况看分身里这个人的话：只确认不复核、主人听每个标出段并判断（真实写入 `segment_fixes`）、疑似段自动排除（`Reviews.settle`，不问人，2026-10-21 起的线上做法）。线上 `settle` 还会把疑似 ≥90%、且 ≥80% 指向同一人的说话人整个改给那个人（`Team.reassign`）；评测没有模拟这一步，仍把这类说话人算作交给主人，手工处理率因此略偏高。

**验收**（负责人 2026-10-20 定）：自动认错为 0；复核后分身里别人的话 ≤ 5%；手工处理率 ≤ 10%（自动归属没决定的说话人，加进入复核队列的说话人，占全部说话时长，每个说话人只算一次）。

**缓存与速度。** 转写结果和声纹按引擎身份存在清单旁的 `library-cache/`，每次运行从它复制一份干净的库，所以只改转写之后的规则时一轮约 2 分钟，不访问转写服务。`--set team.AUTO=0.6` 之类可以不改代码试阈值（可选项见 `TUNABLE`），成绩单写明改过哪些。

```bash
uv run twin eval-asr-library --sessions ~/asr-eval/alimeeting/eval/sessions.jsonl \
  --engines ~/asr-eval/session-engines-4090-prod.toml --out ~/asr-eval/runs/<日期>-<改动> --set team.AUTO=0.5
```

**局限。** AliMeeting 每人只参加一场，样本声音是同场近讲麦克风，与远场说话人质心的相似度中位数只有 0.56（他人最高 0.25）；真实团队里的样本来自同一间会议室的其他录音，相似度更高，彼此也更像。所以这里的自动归属比率偏悲观、认错偏乐观，阈值必须再用真实周会副本检查认错仍为 0。LLM 清洗不在评测里。

**基线（4090，asr-funasr 1.3.3，Eval 8 场）**：自动认错 0；复核后别人的话 3.52%；手工处理率 93.3%（有样本的人 99.4% 的说话时长留给主人，因为 `AUTO = 0.75` 在这里一个都过不了）。降低 `team.AUTO` 时，说话 20–25 秒的短说话人开始被认错，`AUTO_MIN_SECONDS ≥ 30` 可消除：

| AUTO / 最短秒数 | 自动认错秒数 | 复核后别人的话 | 手工处理率 |
| --- | --- | --- | --- |
| 0.75 / 20（现行） | 0 | 3.52% | 93.3% |
| 0.6 / 20 | 45 | 3.82% | 36.2% |
| 0.6 / 30 | 0 | 3.52% | 36.5% |
| 0.5 / 30 | 0 | 3.52% | 27.0% |

剩下的 27% 主要是有样本但声音不够像的说话人（约 21%）和没有样本的人（约 6%）。复核规则 `MARGIN` 0.1 → 0.15 把本人段误标从 6.5% 降到 3.5%、队列从 18 个降到 14 个，但不改变手工处理率。生产阈值尚未修改，等真实周会副本验证。

## 团队录音库线上现状（2026-10-21，daw 只读计数）

`docs/PLAN_VOICE_COLLECTOR.md` 阶段 0 的基线，作为三档自动归属（阶段 3）的对照。在 daw 上用只读脚本计数：只读库里存的声纹，不读音频、不调转写服务，只打印计数，不留文件。当时库里有 55 份录音、583 个说话人、6206 分钟语音。当前转写上的归属是：负责人确认 210 个，自动 273 个，“不认识” 57 个，“多人混在一起” 18 个，未处理 25 个。

**样本。** 41 个有名字的人共有 149 个有效样本，每段录音最多一个。每人中位数 2 个，前 10% 在 8 个以上，最多 15 个：`VOICE_SAMPLES` 只限制每次打标给几个，不限制每人一共有几个。同一人样本两两之间的相似度中位数是 0.713（p10 0.554，p90 0.870）；每个样本和**别人**最像的样本，中位数却有 0.758（p10 0.665，p90 0.877）。有两个以上样本的人里，134 个样本中有 37 个（28%）更像别人的某个样本，而不是自己的其他样本。同一间会议室、同一台设备上，绝对分数靠不住，这和远场认领校准的结论一致。

**自动归属集中在少数人身上。** 273 个自动归属分给了 27 个人：

- 第 1 名被自动归了 58 个说话人，分布在 34 份录音里，共 1915 分钟，占全库语音的 31%。其中 15 个说话人各说了一小时以上，像是主讲人。但有 18 份录音里，ta 被自动归了 2–3 个说话人，也就是追加认领。
- 第 2 名被自动归了 28 个说话人。按今天的样本算，这些说话人里 ta 领先第二像的人的幅度，中位数只有 0.04。
- 有两个以上样本、被自动归过三个以上说话人的 13 个人里，最常命中的那个样本平均拿下 45% 的自动归属，最多的一个人是 100%。

**自动归属一旦做出就不再复查。** 用同一条规则（`AUTO` 0.75、领先 0.15、至少 20 秒）和今天的样本重判这 262 个自动归属：122 个（2395 分钟）结果不变，140 个（883 分钟）今天已经不会自动归属，要退回给负责人；没有一个会改归给别人。原因是 `Team.classify` 只判断没人碰过的说话人，判断时对手的样本还少，后来别人有了样本、领先幅度变小，已经做出的决定也不会撤回。阶段 1 的版本机制只在规则换版本时重判。样本变化时要不要也重判（结果不变的不关闭分身），在阶段 3b 决定。

**现行规则按录音重放。** 逐份录音重放 `Team.classify`，每份都去掉它自己的样本，模拟刚转写完的时候；用负责人的决定当答案：

| 结果 | 说话人 | 分钟 |
| --- | --- | --- |
| 自动归对 | 51 | 464 |
| 自动归给另一个已知的人 | 0 | 0 |
| 自动归给了负责人说“不认识 / 多人”的声音 | 3 | 33.5 |
| 留给负责人：答案是某个人 | 159 | 1558 |
| 留给负责人：答案是“不认识 / 多人” | 72 | 667 |

- 自动归属的语音里别人的话占 6.7%，手工处理率按时长算是 81.7%。
- 每份录音要问的说话人（说话 ≥15 秒且没自动归属）中位数 7 个；10 个说话人以上的录音中位数 9.5 个，p90 14 个，最多 19 个。
- 不在场的人被自动归属：负责人处理完的录音里 1 / 1273，没处理完的录音里 2 / 587。

**局限。** 负责人确认的大多是系统没能自动归属的说话人；已经自动归属的说话人没有人工答案，所以上表的对错率代表的是难判断的那部分说话人，不代表全体。

**对阶段 3 的影响：**

1. 现行规则太保守：按时长 82% 要人处理，大会每场约 9.5 次确认，门槛是 ≤10% 和每场约 6 次。不在场误认很低（3 / 1860），主要靠 0.75 这个绝对下限。所以改成“领先第二名”为主轴时，要盯住不在场误认会不会回升。
2. 追加认领真实存在（18 份录音），“同一录音同一人只自动认一个说话人”有现实意义。
3. 每人样本数没有上限，且 28% 的样本更像别人，所以样本上限、挑选方式和战绩降权（3b.2、3b.3）有必要。
4. 已有自动归属里一半多（140 / 262）按今天的样本已经不成立，新规则发布时（3b.8）会有大量说话人退回负责人。要么连同中档的一键确认一起上线，要么先只重判、不退回，否则负责人的待办会一下子增加。

## 三档自动归属的门槛：daw 跨场按人分两半（2026-10-21）

`docs/PLAN_VOICE_COLLECTOR.md` 的 3a.6。方法和上一节的重放相同：只读，逐份录音去掉它自己的样本，用负责人的决定当答案。规则照 `media/team.py` 的 `tier()`、`_match`、`_prints` 实现。41 个有样本的人按 id 的哈希分成两半，开发半边 20 人，复核半边 21 人。一个说话人算进哪一半，看负责人说 ta 是谁；负责人说“不认识 / 多人”的说话人，被认走时算进被认成的那个人所在的一半。每场确认次数统计全部说话人。“别人的话”指自动归属的语音里不是这个人的时长占比，负责人说“不认识 / 多人”而被认走的说话人整段都算。

**开发半边**，288 组规则：绝对下限 0.5 / 0.6 / 0.7 / 0.75，领先 0.1 / 0.15 / 0.2，最短 20 / 30 秒，同一录音一人一个开或关，样本不限 / 每人 6 个取最不像的 / 每人 3 个取最长的，取最高分或前两个平均。

- 起作用的只有“领先第二名”。领先幅度定了以后，绝对下限从 0.5 换到 0.75、最短秒数从 20 换到 30，结果几乎一样。
- 领先 0.15（现行）：手工 87.8%，别人的话 0%。领先 0.1：手工 63.1%，别人的话 1.8%，大会每场确认中位数 7 次。领先 0.08：别人的话升到 7.5%，超过门槛。
- 前两个样本取平均、限制每人样本数，都没有比“取最高分、不限样本”更好；同一录音一人一个，在这里只少认对的说话人，没有少认错的。
- 领先 0.1 时，剩下 63% 的手工量里，负责人说“不认识 / 多人”的声音占 26.8 个百分点，此前没有样本的人占 5.4 个，首选是对的但领先不够的占 17.5 个，首选不对的占 13.5 个。

开发半边选定：领先 ≥0.1、下限 0.6、至少 20 秒、取最高分、不限样本、不开一人一个。

**复核半边没有通过：**

| 规则 | 认对 | 认错人 | 认走“不认识 / 多人” | 别人的话 | 手工 | 大会每场确认（中位 / p90） | 不在场被认领 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 现行（领先 0.15、下限 0.75） | 36 | 0 | 3（33 分钟） | 9.8% | 75.3% | 9.5 / 14 | 1 / 637 |
| 领先 0.1、下限 0.6 | 69 | 4 | 10（148 分钟） | 21.0% | 44.1% | 7 / 11.5 | 3 / 637 |
| 领先 0.1，“不认识”的声音也当对手 | 54 | 2 | 3（40 分钟） | 8.1% | 57.7% | 8 / 13.5 | 0 / 637 |

“不认识的声音当对手”的意思是：负责人在其他录音里说过“不认识”的声音，也拿来和首选比较，首选要领先它 0.1 才认。这是 `Team._stranger` 的思路，用到认人这一步。在开发半边，它只让手工量从 63.1% 升到 72.6%，错误没有变化；在复核半边，它挡掉了大部分误认。

**结论：**

1. 只靠声纹阈值，这个库达不到“手工 ≤10%”：负责人说“不认识 / 多人”的声音就占了 13–27% 的语音。门槛要么按“有名字的人”的语音来算，要么另想办法自动处理陌生声音，比如把常来的陌生声音自动建成未命名的人，或者自动标成“不认识”。
2. 领先 0.1 在复核半边认走了大量“不认识”的声音，不能直接放宽。加上“不认识的声音当对手”以后，别人的话是 8.1%，仍高于 5%，但已经比现行规则在同一半边的 9.8% 低，手工量从 75% 降到 58%。
3. “认走不认识的声音”算不算错，取决于负责人当时的判断，比如音质差时也可能标成不认识。daw 的数据不能拿回来听，所以这一项只能按负责人的标注计数，可能偏高。
4. 中档（首选领先 0.05–0.1）一键确认的建议，全库约 60% 是对的（23 对 15 错），和计划里的估计一致。所以中档维持一键确认，不先进分身。AliMeeting Eval 上策略 B（先进分身）的别人的话是 14%，同样不达标。

**负责人选定（attribution-v2）：** 领先 ≥0.1、下限 0.6、至少 20 秒，“不认识”的声音也当对手，中档（领先 ≥0.05）一键确认。在复核半边，这套规则别人的话是 8.1%，高于 5% 的门槛，但低于现行规则的 9.8%。所以它作为归属层新版本，和中档一键确认、人物页抽查一起发布，上线后只读计数观察一周。AliMeeting Eval 作为不退化的对照（8 场；样本是同场近讲麦克风，属于上限口径；8 场共有 3 个说话人被认错）：

| 规则 | 自动认错秒数 | 复核后别人的话 | 手工处理率（95% 区间） | 每场确认次数（≥15 秒，平均 / 最多） | 认错落在抽查前 3 条 |
| --- | --- | --- | --- | --- | --- |
| attribution-v1（领先 0.15、下限 0.75） | 0 | 3.20% | 93.29%（84.39%–100.00%） | 20.6 / 39 | — |
| attribution-v2 | 80 | 3.74% | 35.91%（13.54%–59.60%） | 2.1 / 4 | 100% |

v2 下，“已知”的人里 64.6% 的语音被自动认对，0.71% 被认错；中档建议对 12.8%、错 7.3%。“未知”的人（没有样本）中档建议必然是错的，占 34.6%，所以中档只能一键确认，不能先进分身。

## 单麦克风重叠恢复原型（2026-10-13）

评测脚本 [combo_overlap.py](../deploy/asr-eval/combo_overlap.py) 只补丁加载算力包，未修改生产包。模型选择依据：

- [MossFormer2_SS_16K](https://huggingface.co/alibabasglab/MossFormer2_SS_16K)：Apache-2.0、16 kHz、两路单通道分离。ClearerVoice-Studio 报告跨多个合成混合测试集的 SI-SNRi，但没有 AliMeeting CER，不能据此认定能解决真实会议重叠。
- [pyannote segmentation-3.0](https://huggingface.co/pyannote/segmentation-3.0)：权重需接受访问条件。本次未申请权限、未下载，未测重叠检测门控；下述门控是**分离后**的声纹与能量筛选，不节省分离计算。
- [WeSep](https://github.com/wenet-e2e/wesep)：当日主分支 README 的官方预训练模型及本地推理接口仍标为待发布；ClearVoice 的目标说话人提取模型需要视频，不适合单麦克风录音。本次未实测目标说话人提取，也未使用阵列其他通道、头戴麦作为分离输入或参考标注作为检测器。

**实现与边界。** 保留原 VAD、0.65 聚类、Paraformer 和认领相似度。每个输出说话人取最长五段的中心至多两秒，重新计算 CAM++ 均值作混合音频内的登记声纹（不是原窗口聚类内部的精确质心）。原片段按至多八秒送入 MossFormer2，逐块直接调用模型，避开 ClearVoice 包装层的长音频补零及逐路等 RMS 放大。两路都须有足够能量（混合能量的 3%）、与登记声纹余弦至少 0.45、领先次名至少 0.05，且归属不同说话人，其中一路必须是原片段说话人。分离后的 FSMN VAD 裁剪再转写；另一人的文字如果是原文字的子串或相似度达到 0.8 则不添加。门槛是实验启发式，不是经过校准的重叠检测概率。

比较两个策略：`--mode add` 保留原文字，只添加另一人；`--mode replace` 在不超过八秒且两路都有有效输出的原片段上同时替换主路，长片段仍用 add，避免只替换部分而删掉未处理内容。模型只分两路，不能保证恢复三人以上同时说话；聚类没发现的人也无法恢复。仍只处理基线已转出的片段，不解决 VAD 漏检或基线空转写。片段级去重可能丢掉真实的相同附和词；长片段内的第二人追加顺序也会影响先入先出 CER，应同时看 cpCER、本人 CER 与误归属。

## 个人上传路径：重叠感知转写（2026-10-21）

**目标。** 本人上传录音后，记到本人名下的文字要“好”。事先和负责人约定的门槛（Eval 与 Test 都要满足）：本人话语 CER ≤ 20%、本人删除 ≤ 13%、整场 CER ≤ 25% 且删除 ≤ 15%、无重叠句不劣于基线（≤ 12.5%）、他人误归属 ≤ 5%、认错 0 且未认领不多于基线、不在场误认 0 且最高相似度 < 0.5、4090 上 RTF ≤ 0.1、Eval 符号检验 p < 0.05 且 Test 方向一致。基线是线上 asr-funasr 1.3.3：实验实例用 [climb.py](../deploy/asr-eval/climb.py) 加空配置加载同一个算力包，Eval 21 人次的输出与线上逐字一致。

**错误在哪。** 基线的本人错误主要是删除（Eval 25.7%），也就是重叠时段里本人的话整段没转出来：按参考句与他人重叠的比例分档，不重叠的句子错 12%，重叠 ≥ 60% 的句子错一半以上。理想切分诊断（参考时间边界 + 两路分离 + 按参考选路）能把混合音直接转写的 25.0% 降到 17.0%，但用近场声纹选路是 28.7%，比不分离还差：分离后的声音与原声纹不在一个域里。所以要同时解决三件事：找出谁在什么时候说话（允许重叠）、重叠处分开两个人、分开的两路分给对的人。

**方案。** [overlap_pipeline.py](../deploy/asr-eval/overlap_pipeline.py)，由 climb.py 的 `pyannote` 配置项接入，替换 `Engine.transcribe`，输出格式不变：

1. 响度归一：按能量最高的 30% 个 30 毫秒帧把整场归一到 −27 dBFS，声纹、分离和识别都用归一后的音频。单独用在基线上，本人 CER 从 31.67% 降到 26.84%（15 好 6 差，p = 0.078），收益集中在一场小声的会议。
2. 分人换成 [pyannote speaker-diarization-community-1](https://huggingface.co/pyannote/speaker-diarization-community-1)（CC-BY-4.0，需在 Hugging Face 同意使用条件），重叠版输出，VBx 聚类 `Fb` 从默认值改为 0.6（Eval 上修复了一场漏掉第 4 人的问题）。完全落在别人发言段里、又短于 0.5 秒的段去掉：这类段在参考里多半只有别人在说话。
3. 重叠处用 MossFormer2_SS_16K 分成两路（前后各带 0.5 秒），两路按“分离域”声纹分给重叠区里说得最久的两个人：每人取几段 3 秒单人语音过同一个分离器，取能量大的一路求均值。
4. 每人的段合成不超过 15 秒的块，块里不属于此人的时段静音，重叠区换成此人那一路；识别用 FireRedASR2-AED（beam 1，循环输出改用 Paraformer 重转，见上文）。
5. 认领用的声纹只取单人时段的 1.5 秒窗口。

**Eval 爬山（8 场，21 人次）。** 每一步只改一项；“好 / 差”是与上一行逐人次比较本人 CER。

**结论：在 AISHELL-4 上校对不降低错字率，略升 0.02–0.04 点。** 原因：
- **参考文字逐字记下说话人的口误。** 抽看改错的修改，多数是识别器照原声转对了，LLM 改成了说话人想说的词，例如“要委转要婉转→要委婉要婉转”“标查标识→检查标识”“在学在校→在校”“主体特销→主题特价”。对读者是改好了，CER 按原声算就是改错。
- **提示词要求保留的重复字仍会被删。** 如“有有→有”“时时间→时间”“房房监局→房监局”，参考里都保留了，删除率因此从 4.69% 升到 4.71–4.74%。这是线上同样存在的问题，后续可以收紧提示词或在程序里拒绝只删重复字的修改，改了要重测。
- **能修的错误本来就少。** 1.4.0 的剩余错误以重叠语音里的删除和插入为主，替换只有 6.63 点；LLM 没有音频，补不回删除。真正的同音纠错（如“事务科→事故科”“病人→隐患”）占比小，另有个别改坏（“二零一一年→二零二一年”）。

这和 L4 在 AliMeeting 上的结论一致：公开会议集是日常话题、逐字标注，量不出校对的收益；校对的价值在术语多的真实会议上（讲课录音 89 处修改全部改对，见[真实录音复核与上线](#真实录音复核与上线2026-10-14)）。校对是给记忆整理用的：把口误改成本来想说的词，对检索和记忆是改好了，只是不再逐字忠实于原声。所以对外的 AISHELL-4 成绩报识别器原始输出，不报校对后的数字。

## 录音降噪与去混响（2026-10-21）

**问题**：真实周会录音有环境噪音和人声失真，转写前先做声学增强有没有用。

**做法**：从一段 137 分钟的真实周会（本机副本，13 人，整场中位信噪比约 19 dB，没有削波）里按每 30 秒估计信噪比，挑出最差的 4 段，每段 2.5 分钟（信噪比 15.1–15.7 dB），拼成 10 分钟。在 4090 上用四种处理各跑一遍，原声和处理后的版本都用线上转写服务（asr-funasr 1.4.1）转写，不做 LLM 校对。没有人工参考文字，所以先比字数和与原声版的差异；每处差异由文字模型盲评（两种读法随机排序，看哪种更像原话），再由用户试听抽查。录音、转写和试听片段只留在本机和 4090，不入库。

| --- | --- | --- | --- | --- | --- | --- |
| 原声 | — | 3201 | 574.6 秒 | — | 5 | — |
| WPE 去混响（nara_wpe，CPU） | 8 秒 | 3205 | 573.5 秒 | 2.4% | 5 | 11 / 11 / 4 |
| FRCRN_SE_16K 降噪 | 19 秒 | 2236 | 498.7 秒 | 37.5% | 4 | — |
| MossFormerGAN_SE_16K 降噪 | 47 秒 | 3201 | 582.5 秒 | 10.2% | 5 | 49 / 69 / 26 |
| MossFormer2_SE_48K 降噪 | 14 秒 | 3201 | 580.1 秒 | 6.7% | 5 | 33 / 55 / 24 |

**结论：增强不进转写链路。**
- FRCRN 吞掉 30% 的字和 76 秒语音，还少分出一个人。
- 两个 MossFormer 降噪字数不变，但改坏的多于改好的；用户试听差异处也认为转写没有帮助，有些更差。
- WPE 几乎不改变转写，这段录音的混响不重。
- 这和业内的经验一致：单通道增强会留下识别器没见过的处理痕迹，接在抗噪的识别器前面往往持平或变差。

**但降噪后听起来好很多。** 用户盲听三组 20 秒 A/B（原声和 MossFormer2_SE_48K）：降噪版明显更清楚。所以降噪只适合用在试听播放上（例如确认说话人时试听一句），识别、分人和声纹仍用原声。MossFormer2_SE_48K 处理 137 分钟约 3 分钟 GPU。

局限：只有一段录音、10 分钟，噪声中等，没有测到削波一类的失真；结论是“没有看到收益”，不是“任何录音都不会有收益”。

## FireRed BF16 与增量解码（2026-10-22，asr-funasr 1.5.4）

本次只改变 FireRed 的推理精度与解码：支持原生 BF16 的 CUDA 使用 BF16；beam=1 按 token 缓存 self-attention 的 K/V，并用 SDPA 计算 attention。其他模型、分人和复读回退规则不变。包和转写版本均为 1.5.4，因为浮点精度变化可能改变少量文字。

### 固定句段质量验证

AliMeeting 20 场会议按固定哈希每场最多取 100 句，共 1438 对远场／近讲音频、2876 条、2.412 小时，每个视角 20426 个参考字。三组共用相同音频、权重和 beam=1；不经过分人、分离、补标点或 LLM 校对。下表耗时是该批 FireRed 推理总耗时，不能视为整条转写流程加速。

| 方案 | 远场 CER | 近讲 CER | 合计 CER | 推理耗时 |
| --- | --- | --- | --- | --- |
| FP32 原解码 | 4.2789% | 2.3402% | 3.3095% | 253.24 秒 |
| BF16 原解码 | 4.3033% | 2.3255% | 3.3144% | 140.07 秒 |
| BF16 + 增量解码 + SDPA | 4.3180% | 2.3353% | 3.3266% | 110.14 秒 |

组合方案远场 CER 差值为 +0.0392 个百分点，按会议配对重采样的 95% 区间为 [+0.0133, +0.0658]；近讲为 −0.0049 个百分点，区间 [−0.0479, +0.0314]。严格和去语气词两个口径的区间上界都低于预先设定的 +0.3 个百分点。原文有 27 条变化，归一化后 8 条改善、15 条变差，其余不影响 CER；最差单句多 2 个错误。没有新增空输出或复读，空输出从 12 条变为 11 条。此结果支持小幅质量变化在预设容忍范围内，不代表文字逐字一致。

### 整场流程验证边界

**发布时状态：回归仍在运行，尚无整场配对质量结论。** 本次依据上述句段质量验证、解码一致性与服务自检发布；以下记录回归设计及已观察到的显存限制，不能视为整场验收通过。

使用 AliMeeting Eval 全部 8 场会议（4.205 小时、21 份本人参考声音），经真实 HTTP 上传和 NDJSON 流式返回，覆盖分人、分离、FireRed、复读回退、补标点和声纹归属。不调用 LLM 校对。整场 CER、cpCER、本人话语 CER 的配对差值按会议重采样，验收要求 95% 区间上界不超过 +0.3 个百分点；另外核对新增失败、分人和归属变化，以及静音、低幅噪声、批量声纹和强制复读回退。

验证机器是 RTX 4070 Laptop 8 GiB。原 FP32 版本以默认模型常驻方式跑整场时显存不足；仅卸载 FireRed 与分离权重仍会在识别阶段显存不足。因此对照程序把闲置的大模型权重暂存 CPU，串行调度，所有模型计算仍在 CUDA 上以原精度完成，batch=8 不变。候选版本使用默认常驻和并行补标点流程。两组耗时不可直接用来计算整条流程的加速比，失败尝试单独保留。

## 缓存自动归属基线（2026-10-26）

`twin eval-asr-attribution` 复用整场清单、`eval-asr-session` 的转写缓存和参考音频声纹缓存，只调用当前 `Team.classify`。**每场建立独立临时库**，登记相同的参考人物；不会把上一场按金标模拟的确认或新建人物传给下一场，评分用的金标也不会把新建匿名人物变成“认出了已知人物”。不调用转写服务或大模型，不运行逐段复核。它补充归属层的可复现基线，不能替代 `eval-asr-library` 的完整流程评测。

```bash
uv run twin eval-asr-attribution \
  --sessions "$EVAL_ROOT/alimeeting/eval/sessions.jsonl" \
  --cache "$EVAL_ROOT/baseline/session-cache.jsonl" \
  --enrollment "$EVAL_ROOT/baseline/voiceprints.jsonl" \
  --provenance "$EVAL_ROOT/baseline/provenance.json" \
  --out "$EVAL_ROOT/runs/attribution-baseline" --split all
```

- `cache` 沿用整场缓存的 JSONL 行：`session`、`target`、`segments`、`speakers`、`seconds`；`speakers` 必须有有效的 `embedding`。目标为清单中排序后的第一份参考声音；没有参考声音时为空字符串。
- `enrollment` 沿用库评测的 JSONL 行：`{"key":"voice:<参考音频SHA256>","embedding":[...]}`。缺少会议、参考声纹或维度不兼容时直接失败，**不会自动访问模型补齐**。`provenance` 显式记录公开数据及人工标注来源、转写与参考声纹的产出版本和已知局限；工具保留这些声明，不自动把任意标签当人工真值。
- `--split dev/formal` 按固定种子 `attribution-meetings-v1` 将会议分成两组；声明过 `group` 的会议整体分组。每组只使用本组清单的参考声音；会议 ID、组、种子、数据/音频/代码摘要、实际阈值写进成绩单。区间按会议或声明的组 bootstrap。**已有调参数据重新分组不会重新变成未见过的留出集**。
- 清单中的 `voice_from` 用来统计同场、异场或来源未声明的参考声音。同场近讲麦克风样本仍会偏乐观；会议切分不等于跨会议声纹泛化，来源未核实时 `cross_meeting_enrollment_verified=false`。
- JSON/Markdown 成绩单默认权限 `0600`，只含指标、计数和来源摘要，不复制会议原文、音频或向量；临时库结束后删除。输出仍应放仓库外。

### 指标口径

| 指标 | 分子 / 分母或计数 | 边界 |
| --- | --- | --- |
| 已知人物自动覆盖 | 自动归给有参考声音人物的说话人秒数 / 可按金标评分的说话人秒数 | 自动新建未命名人物单列，不能算认出了已知人物；不是原始音频覆盖率 |
| 自动归属错误时间 | 自动认领区间内，只有其他人在说话的时间 / 本人或其他人在说话的时间 | 复用 `spoken_by` 的 10 毫秒帧口径，静音不计分母；本人同时说话的重叠区不计错，属于有限口径，不是最终记忆污染率 |
| 错归整簇时长代理 | 簇的多数金标人物与自动归属不同的说话人秒数 | 多数正确的簇也可能混入他人，不能只看这一项 |
| 人工确认语音占比代理 | 尚未自动决定的说话人秒数 / 可评分说话人秒数 | 不含未命名人物命名、跨场声音分组、试听、抽查、逐段复核；不是人工工时 |
| 确认次数代理 | 未决且至少 15 秒的说话人数，每场平均和最多次数 | 声音分组或片段复核会改变实际点击数；不直接代表界面待办数 |

同时报告没有金标语音覆盖的假设时长；它不冒充可评分样本。新指标保留分子、分母和区间；分母为零时比率为 `null`，不记作零错误。`actual_human_seconds` 始终为 `null`，除非另行做真实用户计时，本工具不根据语音时长猜测工时。
